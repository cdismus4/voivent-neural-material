# Voivent Neural Material（VNM1）能力表

- 対象形式：VNM1 version 1（4ファイル構成：manifest.json／weights.bin／level-0.bin／tail.bin）
- 本書の数値はすべて測定記録の実物に基づく。宣伝文句は置かず、失敗と制限も同じ表の中に書く。
- 作成：2026-11-20

## 1. 判定ゲート（品質の物差し）

学習済み素材が「合格」とされる条件は次の全項目を同時に満たすこと。

| 項目 | 基準 |
|---|---|
| Base Color PSNR（線形空間） | ≥ 35 dB |
| スカラー MAE（Roughness／Metalness／AO、各チャンネル） | ≤ 0.02 |
| 法線角度誤差 平均 | ≤ 3° |
| 法線角度誤差 p95 | ≤ 8° |
| 容量 | 参考指標として BCn フル mip チェーン比を記録（ゲート自体は §3 の容量ゲートを参照） |

- 入力に無いチャンネル（定数として記録されるチャンネル）はゲート対象外とし、「欠測」として記録する。
- 検証の基準解像度は 2048²。それ以外のサイズは「検証範囲外」としてレポートに記録される。

## 2. プロファイル

潜在グリッドのサイズはプロファイルごとに固定で、入力テクスチャのサイズには依存しない（この性質が §6 の 4096² の壁と、小さいテクスチャでの容量膨張の両方の原因である）。

| プロファイル | ファイル総容量（実測） | level-0（VRAM 常駐分、RGBA8） | 潜在テクスチャ枚数 | 復号コスト（MACs/テクセル） |
|---|---:|---:|---:|---:|
| standard | 約 1.32 MB | 1,310,752 B（約 1.31 MB） | 2 | 1,056 |
| standard8 | 約 2.63 MB | 2,621,472 B（約 2.62 MB） | 4 | 1,248 |
| quality | 約 5.25 MB | 5,242,912 B（約 5.24 MB） | 2 | 1,664 |
| quality8 | 約 10.50 MB | 10,485,792 B（約 10.49 MB） | 4 | 1,920 |

- VNM1 の容量はプロファイルでほぼ決まり、入力の画素数では変わらない。BCn は画素数×マップ数で増えるため、容量比は入力サイズに強く依存する。

## 3. 判定結果（30素材）

Poly Haven CC0 2K 素材 24 点＋パイロット 6 点、計 30 素材について、ラダー（standard → standard8 → quality → quality8、＋僅差時の調整 1 回）で「一番安い合格構成」を探した結果。

- **30 素材中 29 素材に合格構成が存在する。**
- 最安合格構成の分布：standard 4／standard8 2／quality 14／quality8 8／quality8＋調整 1
- 合格構成の容量比（対 BCn フル mip チェーン）：0.079〜0.626
- 測定規模：GPU 631.1 分（上限 720 分）、74 カーネル、費用 $0

### sand の出自（読み違い防止のため明記）

- sand（coast_sand_03）は**初期ラダーでは不合格**だった（quality8・既定条件で色 34.38 dB、AO 0.0219）。段3 本体の集計ファイルでは今も不合格として記録されている。
- その後の調整ランで、quality8＋色重み 6＋スカラー重み 3＋150k 反復により**全項目合格**した（色 35.31 dB／AO 0.0138／粗さ 0.0042／法線 平均 1.96°・p95 4.86°／容量比 0.6257）。「29/30」はこの調整ランの記録を含む数字である。

### パイロット由来 3 素材の出自（読み違い防止のため明記）

最安合格構成の分布には、段2 パイロット由来の 3 素材が次の条件で含まれている。いずれも段3 ラダーの既定条件（既定の重み・50k 反復）そのままの測定ではない。

- **wood**：standard で合格だが、スカラー重み 3.0（既定 1.0）の調整条件での測定（色 44.72 dB）。分布では standard の 1 件として数えている。
- **paint**：quality で合格だが、色重み 6.0＋150k 反復の調整条件での測定（色 35.73 dB）。分布では quality の 1 件として数えている。
- **stone**：合格の測定は VNM1 正式形式ではない形式変種（潜在チャンネル数を変えた「quality8ch」、MLP 入力次元 20）での測定（色 36.80 dB）であり、正式プロファイル quality8 での測定ではない。分布では quality8 の 1 件として数えている。

したがって「29/30」は、正式形式・既定条件のラダーだけで得た数字ではなく、上記の調整条件および形式変種での測定を含む構成である。

### leaves（唯一の未達）

- leaves（forest_leaves_02）は最強の調整（quality8＋色 6＋スカラー 3＋150k 反復）でも色 PSNR 31.46 dB に留まり未達。AO（0.0197）・粗さ・法線はゲート内に入ったため、未達要因は**色の表現力のみ**と切り分け済み。細密な有機模様の色再現が本方式の限界として実測で確定している（§6）。

## 4. 実務コーパス検証（ガチテスト）

判定ランとは別ソース・別条件の素材での通し検証を 2 回行った。

### 第1弾（14素材、CC0、ambientCG／Kenney）

- 結果：**11 合格／2 不合格／1 件は設計どおり入力段で拒否**（Base Color に実アルファを含む素材。アルファは未対応のため exit 2 で理由つき拒否）。
- grass001-2k（2048²）：不合格。色は合格圏（35.00 dB）だが粗さ MAE 0.0298・AO MAE 0.0306 が未達。自動調整の発動条件に AO が 0.0006 差で届かず不発だった（条件の崖）。後の実験で調整を手動発動しても未達であり、原因は発動ルールではなく容量側と切り分け済み。
- ground037-4k（4096²）：不合格。最高段 quality8 でも色 PSNR 20.78 dB。潜在グリッドが固定サイズのため、入力が大きいほど 1 セルあたりの負担が増える（§6）。
- 容量は当時ゲート対象外で、BCn より大きくなる書き出しでも合格になった（雪素材で比 1.25、64×64 素材で比 240）。この所見を受けて容量ゲートを実装した（§6）。
- 1ビット PNG のスカラーマップが静かに壊れるバグを発見（金属度が実質 0 のまま「合格」表示になる）。入力層のみを修正し、再検証で復号した金属度の平均が 0.99985（修正前 5.15e-5）に戻ったことを確認済み。
- 学習コストは解像度でなく反復回数で決まる：1 段（50k 反復）で約 7〜11 分（T4）。64×64 でも 4096² でも同程度。

### 第2弾（12素材、実ベンダー ARM・JPEG・EXR・破損入力・合成フィクスチャ）

- 学習した 9 素材は**全て最初の段 standard で合格**。ただし今回の素材群は第1弾より易しい（定数スカラーの素材が多い）ため、「9/9」を第1弾と同格の難易度の証拠として読まないこと。
- **ARM パックマップの意味的失敗（重要）**：Poly Haven の ARM（R=AO／G=粗さ／B=金属度）を粗さ枠にそのまま置いた素材は、数値ゲートを合格した。しかし復号された「粗さ」は実は AO であり、本物の粗さとの MAE は 0.1544（上限 0.02 の約 7.7 倍）だった。**ゲートは「どのマップか」の意味の取り違えを検出できない。** preflight ではパックマップ疑いの警告が出るが、train の結論面にはその警告が引き継がれない（製品上の未決事項）。
- 入力の拒否系：JPEG セット・EXR は exit 2 で理由つき拒否。途中で切れた PNG は当初トレースバックで落ちたが、修正後は exit 2 の入力エラーになる。
- 合成フィクスチャの所見：文字看板は原寸で判読可能（色 64.50 dB）。16bit グラデーションの微小段差（+3 LSB/行）は段差としては保存されず、±0.003 程度の波打ちを伴う滑らかな坂として再現された（実用上のバンディングとして見える水準ではない）。AO をベースカラーに焼き込んだ素材は暗部の階調が保たれた。
- 測定規模：Colab T4、GPU 72.4 分、CU 消費 5.69。

## 5. 復号の正確さ（適合性）

- ゴールデンベクタ：4 プロファイル × 286 ケースで CPU 参照実装と照合する適合テストを備える。
- 第三者監修（Gemini Task／Neon、2026-11-20）：仕様文だけからの独立再実装が全 4 プロファイルで適合し、最大絶対誤差は 2.2e-08〜3.0e-08 だった。製品テスト 143 件の実走・preflight の実走も採点キーと一致した。
- GPU デコーダ（Three.js WebGPU／TSL）：デスクトップ（Apple Metal-3）と Pixel 9a 実機（ARM Valhall）の両環境で検証済み。
  - 2進格子上の読み戻し検証：最大誤差 4.77e-7〜7.15e-7（両環境・全プロファイル）。
  - 実アセット 4 点（64×64＝4,096 点照合）：最大絶対誤差は生値で 1.79e-7〜6.56e-7、PBR 後処理後でも最大 1.34e-5。いずれも目安 1e-4 の内側。
  - **任意 UV での照合では最大 1.20e-4〜1.81e-4 の差が出る**（RMSE は 1.8e-5〜3.0e-5）。これは GPU のテクスチャユニットによる RGBA8 バイリニア補間がサブテクセル位相を 1/256 刻みで量子化するために生じるもので、CPU 参照（float の厳密補間）との差である。格子点上では上記のとおり 1e-7 級で一致する。CI の合否判定はサンプリング種別で閾値を分ける前提が要る。

## 6. 復号コスト実測

計測手順：ウォームアップ 60 フレーム＋計測 300 フレーム、同一シーン・同一カメラで通常 PBR テクスチャ参照に置き換えたベースラインとの差分（Δ）。frame_ms は render()＋onSubmittedWorkDone() の壁時計。

### デスクトップ（HeadlessChrome 158、apple / metal-3、1280×720、DPR=1）

ベースラインのフレーム時間中央値は占有率 25%／50%／100% で 2.2／2.1／2.0 ms。

| プロファイル（素材） | Δ 25% | Δ 50% | Δ 100% | 100% 時 GPU timestamp 中央値 | コンパイル |
|---|---:|---:|---:|---:|---:|
| standard（marble） | +0.5 ms | +1.3 ms | +2.7 ms | 5.639 ms | 39.5 ms |
| standard8（fabric030） | +0.6 ms | +1.6 ms | +3.3 ms | 6.846 ms | 44.4 ms |
| quality（cloth） | +2.3 ms | +4.7 ms | +8.8 ms | 17.604 ms | 38.5 ms |
| quality8（sand） | +2.9 ms | +5.8 ms | +10.9 ms | 21.956 ms | 44.3 ms |

- デスクトップではコスト増が MACs/テクセルにおおむね比例して見える。高解像度で画面全面に quality 系を敷く使い方は注意が要る。
- 注記：この環境の timestamp-query 値は壁時計の約 1.6〜1.7 倍を返す癖があり、フレーム制約の評価には frame_ms（壁時計）を用いること。JSON には両値をそのまま記録してある。

### Pixel 9a 実機（Chrome 157、arm / valhall、DPR 2.625）

- 実画面ネイティブ（1079×2208、238 万画素）：GPU 時間 1.38〜1.51 ms、フレーム全体 5.6〜6.1 ms（占有率 100% 時）。通常 PBR ベースラインとの差は、占有率 100% では全プロファイルで ±0.5 ms 以内（実測 −0.2〜+0.3 ms）。ただし占有率 25% では quality +1.9 ms・quality8 +1.1 ms の外れがあり、「全条件で ±0.5 ms 以内」ではない。
- 極限条件（3360×1890、635 万画素）：GPU 時間 4.19〜4.92 ms、フレーム全体 7.1〜7.6 ms。
- 基準条件（1280×720、DPR=1）でも Δ は ±0.5 ms 級。別途保管した実測 JSON のランでは Δ は −0.8〜+1.6 ms の範囲で、ランごとにこの程度のばらつきがある。
- 初回シェーダコンパイルは 80〜233 ms。実運用ではプリウォーム（compileAsync 等）の設計が重要になる（§7 の所感も参照）。
- 重みとシェーダは分離されているため、同じプロファイル内では素材が増えてもシェーダ本体（WGSL）は不変であることを実装側で確認済み。素材数に比例してコンパイルが増える形にはならない。

### VRAM と使い分け（実装者所感を含む）

- level-0 は RGBA8 非圧縮の潜在テクスチャとして常駐する。常駐量は §2 のとおり standard 約 1.31 MB／standard8 約 2.62 MB／quality 約 5.24 MB／quality8 約 10.49 MB（いずれも 1 素材あたり）。
- 多数マテリアルを常駐させる用途では、quality 系は VRAM が重めになる。**standard／standard8 を標準とし、quality 系は主要素材に限る使い分けが現実的**というのが、両実機で実装と計測を一通り触った実装者（あんち）の所感である。特に standard8 は 2.62 MB で、Pixel 9a 実画面ではベースライン比 +0.5 ms 以内に収まっており、バランスが良いという評価だった。
- これは所感であり、多数マテリアル同時常駐の実測はまだ行っていない。

## 7. 目の確認の所見（数値と目の一致・不一致）

平らなテクスチャ同士の比較での所見である。エンジン内での見え方（照明・角度・距離）は未確認（§8）。

- 合格素材 6 点のシート（原画／復号／誤差）では、復号時の PSNR 再計算が記録値と Δ±0.0000 dB で一致することを確認した上で目視した。合格組は原画と見分けがつかず、これは成功の形である。
- leaves は数値の未達どおり、葉の細部が溶けて見えた。数値と目が一致した代表例。
- 不合格の ground037（4096²）は小石の粒構造が溶けて全面がぼやけた。grass001 は大まかな流れは残るが細部が溶けた。
- 合格していても、拡大すると細部の軟化は見える。例：grass の粗さの粒は面全体で均され気味になり、濡れアスファルトなど粒状感のある素材でも粒の質感は弱まる方向に出る。ゲート合格の見え方と矛盾はしないが、「無劣化」ではない。
- 色だけのシートでは、粗さ・AO で落ちた理由が絵で見えなかった（第1弾の盲点）。第2弾からシートを色／法線角度／スカラー誤差の 3 段構成に改めた。
- 16bit グラデーションの微小段差は、数値上は合格（63.12 dB）でも段差としては保存されず滑らかに再現された。「数字が良い＝元の構造がそのまま残る」ではない例。

## 8. 制限・未対応・既知の失敗パターン

| 項目 | 内容 |
|---|---|
| 細密な有機色 | leaves 型（細かい葉・有機模様）の色再現は方式の壁。最強調整でも 31.46 dB（基準 35）。 |
| 4096² 入力 | 潜在グリッド固定のため品質が崩壊する（20.78 dB）。格子を 2 倍にする実験では 27.91 dB まで回復したが未達（反復回数固定の交絡あり）。製品形式のグリッドは固定のまま。 |
| 小さい・薄い素材 | 容量がプロファイル固定のため、入力が小さいほど容量比が膨らむ（64×64 で比 240 の実測）。対策として容量ゲートを実装済み：最安の standard でも BCn 見積もりを下回れない素材は入口で exit 2 拒否（`--allow-capacity-expansion` で上書き可、レポートに記録）。仕上がりの容量比が 0.9 以上／1.0 以上では警告を出す。 |
| パックマップ（ARM／ORM） | 分割せずにスカラー枠へ置くと、ゲートは意味の取り違えを検出できない（§4 第2弾）。preflight の警告のみが手がかりで、train の結論面には載らない。利用側でチャンネル分割してから渡すこと。 |
| アルファ（切り抜き） | 未対応。実アルファのある Base Color は入力段で理由つき拒否される。 |
| Emissive／Height 等 | 未対応。標準セット外のファイル（displacement、emissive）は現状、無言で無視される（警告は出ない）。 |
| 入力形式 | PNG のみ。JPEG／EXR は exit 2 で理由つき拒否。 |
| 中間 mip・異方性 | 既知の制約：現行ランタイム（TS／Godot とも）の復号は mip 0 の直評価で、中間 mipmap レベルでの評価・ブレンドを行わない。そのため遠景など強く縮小される条件では縮小モアレ（チラつき）が出る（公開デモと README に VNM1 v1 の制約として明記済み）。背景として、現行アセットは normalizedMip＝0 固定で学習されており、mip 対応は将来の学習方式の課題（v2 検討事項）。形式と復号の定義自体は normalizedMip 入力を持つ。なお tail 遷移部と異方性フィルタリング時の品質は未測定のまま。 |
| エンジン内での見え方 | 照明・角度・距離を変えた実描画での品質は未確認。本書の目視所見は平らなテクスチャ比較に基づく。 |
| デスクトップでの全面敷き | quality8 を画面全面・高解像度で使うと +10.9 ms 級の追加コスト（§6）。 |
| VRAM 常駐量 | quality 系は 1 素材 5.24〜10.49 MB が常駐する。多数常駐の用途では使い分けが要る（§6）。 |
| 本番シーンへの配線 | 本番 3D シーンへの配線は TSL デコーダの GPU 直結に一本化済み（CPU ベイク経由は撤去）。GPU デコーダ自体はデスクトップ／Pixel 9a 実機で検証済み。 |
| シード依存 | ゲート結論はシードで動かないことを境界素材 2 点で確認済み。ただし grass の色 PSNR は線を挟んで ±0.16 dB で揺れ、色単独の判定はシードで反転しうる位置にある。 |

## 9. 試して採用しなかった改善案（測定済み）

いずれも「効くかもしれない」で済ませず、実測して結論を出したもの。

| 案 | 結果 |
|---|---|
| 潜在への汎用可逆圧縮（zlib／lzma 等） | 157 資産の実測で最良でも総容量 −8.4%。容量対策の本命にはならない。 |
| 誤差集中部への局所手当て（疎残差タイル） | 不合格素材ほど誤差は面全体に拡散しており、合格素材の方が集中度が高かった。前提が崩れたため見送り。 |
| 二段階 QAT（終盤で潜在を凍結し MLP のみ微調整） | 3 素材で救済なし（不合格は不合格のまま、対照の合格素材は −0.14 dB）。現行レシピの終盤 QAT で量子化誤差は処理済みと読める。不採用。 |
| 学習済み初期化器（小規模 CNN で初期グリッドを予測） | 到達反復 20% 以上減は 5 素材中 1 素材のみで、悪化も 2 件。初期化器の学習自体が平均予測レベルで頭打ちだった。この構成では信号なし。初期化一般の否定ではないが、本格版へ進む根拠は得られなかった。 |

## 10. 再現と検証の材料

- 適合テスト：ゴールデンベクタ 4 プロファイル × 286 ケース。
- 製品テスト：143 件（第三者監修時にも実走で一致を確認）。
- 本書の各数値の出典対応は、同梱の作成時ノート（CAPABILITY_NOTES.md）に記録してある。
